# 팀 메시지 보관함 — 설계 초안 (미채택)

> 상태: **설계 초안** (2026-10-29 사용자 요청). 코드 없음.
> 🔴 이 기능은 **Spec 원칙 1(Zero Retention) · 필수 5 · CLAUDE.md 금지 1번과 정면으로 충돌한다.** 채택하려면 §8 「0단계」의
> 정책 개정을 사용자가 승인해야 한다. 승인 전에는 이 문서가 무엇을 적든 본문 저장 코드를 쓰지 않는다.

## 금지 (채택 후에도 유지)
- 동의 없는 저장 금지 — **팀 관리자가 켜는 것만으로는 저장하지 않는다.** 팀원 본인의 동의가 있어야 한다.
- **받은 메시지(상대방이 쓴 글) 자동 저장 금지**(1단계). 상대방은 사이 이용자도 아니고 동의한 적도 없다.
- 민감정보 차단(키·카드번호·주민등록번호)에 걸린 글은 저장하지 않는다 — 차단은 보관함 앞에서도 그대로 돈다.
- Worker·서버 **로그에는 여전히 본문 금지** — 보관함은 정해진 Firestore 경로 하나에만 쓴다.
- 보관된 글로 **개인 점수·순위·평가를 만들지 않는다**(Spec 원칙 2).
- AI 학습에 쓰지 않는다(Spec 원칙 4). 활용 기능에서 Claude로 보낼 때도 지금과 같은 API 조건.

## 2. 무엇을 저장하나 (1단계)

| 대상 | 1단계 | 이유 |
|---|---|---|
| **내가 보낸 글** — 원문 + 적용한 다듬은 결과 | **예** (동의한 팀원만) | 본인이 쓴 글이고, 팀이 「우리가 이렇게 보냈다」를 쓰려는 핵심 |
| 회신 초안 | 적용한 것만 (= 보낸 글) | 만들기만 하고 버린 초안은 저장하지 않는다 |
| 뜻 풀기 대상(받은 글) | **아니요** | 제3자 개인정보. 3단계에서 「직접 저장」 버튼 + 이름·주소 가림을 검토 |
| 직전 대화 맥락(최대 5개) | **아니요** | 상대방 글이 섞인다 |
| 민감정보 차단에 걸린 글 | **아니요** | 금지 3 |
| 메타데이터 | 예 | 시각 · 작성자 uid · 대상 언어 · 톤 · 긴급도 · 받는 사람 지역(이름·메일은 넣지 않는다) |

## 3. 동의 — 저장하는가 판정표 (위에서부터 처음 맞는 줄)

| # | 조건 | 저장 |
|---|---|---|
| 1 | 팀 요금제가 아님 | 아니요 |
| 2 | 팀 관리자가 보관함을 켜지 않음 | 아니요 |
| 3 | 팀원 본인이 동의하지 않음 · 철회함 | 아니요 |
| 4 | 이번 메시지에서 「팀 보관함에 저장」을 끔 | 아니요 |
| 5 | 민감정보 차단에 걸림 | 아니요 |
| 6 | 그 밖 | **예** |

- 관리자: 팀 설정에서 켬 + **보관 기간**(30 · 90 · 365일 중 선택). 끄면 이후 저장 중단, 기존 글은 기간까지 남거나 「전체 삭제」.
- 팀원: 보관함이 켜진 팀에 있으면 첫 다듬기 전에 동의 화면. 언제든 철회 — 철회하면 이후 저장 중단 + 「내 글 모두 삭제」 선택.
- 메시지마다: 다듬기 팝업에 「팀 보관함에 저장」 표시·토글. 켜진 상태에서는 팝업의 「Zero Retention」 표시를 「팀 보관함에 저장됨」으로 바꾼다(거짓 표시 금지).
- 팀을 나가면: 그 사람의 글은 삭제(기본). 관리자가 남기려면 본인이 나가기 전에 동의해야 한다 — 🟡 결정 필요.

## 4. 활용 — 기능 후보

| 기능 | 무엇 | 단계 |
|---|---|---|
| 팀 보관함 보기·찾기 | 받는 사람 지역·언어·기간으로 거르고 최근 순으로 본다 | 1 |
| 내 글 지우기 · 관리자 전체 지우기 · 내보내기 | 작성자·관리자 권한 | 1 |
| 다듬기 때 「팀이 비슷하게 보낸 글」 참고 | 같은 언어·톤의 과거 글을 프롬프트 참고로(본인 동의 범위 안) | 2 |
| 팀 용어집 후보 제안 | 자주 고쳐지는 표현 → 관리자가 승인하면 팀 용어집에 | 2 |
| 신규 팀원 예시집 | 관리자가 고른 글 묶음 | 2 |
| 받은 글 직접 저장 | 이름·메일 가림 후 저장 | 3 |

## 5. 저장 구조

| 항목 | 설계 | 근거 |
|---|---|---|
| 경로 | `teams/{teamId}/archive/{msgId}` (Firestore 서울) | 팀 용어집과 같은 위치 규칙(`firestore.rules` `teams/{teamId}/glossary`) |
| 필드 | `authorUid · createdAt · expireAt · original · refined · targetLanguage · tone · urgency · recipientRegion`만 (화이트리스트) · `original`·`refined` 각 4,000자 상한 | 팀 용어집 규칙과 같은 방식 |
| 쓰기 | **Worker만** (서비스 계정). 클라이언트 쓰기는 규칙으로 `false` | 요금제·동의·민감정보 판정을 서버에서 해야 우회가 안 된다 |
| 읽기 | 그 팀의 팀원만 (`isMember()`) | 팀 id를 아는 것과 팀원인 것은 다르다(기존 규칙 주석) |
| 삭제 | 작성자 본인 · 팀 관리자 · `expireAt` 자동 삭제(Firestore TTL — Spark에서 되는지 확인 필요, **추정**) | 보관 기간 약속을 지킨다 |
| 암호화 | 1단계는 Google 기본 저장 암호화만. 필드 암호화는 검색·활용을 막고 키 관리(KMS)는 GCP 비용 → 2단계 검토 | 비용 0 원칙 |
| 검색 | Firestore는 전문 검색이 없다 → 1단계는 거르기 + 최근 순. 본문 검색은 2단계(외부 검색 서비스 = 비용) | — |

## 6. 용량·비용 (추정)

| 항목 | 계산 | 결론 |
|---|---|---|
| 글 1건 | 원문 + 결과 + 메타 ≈ 2~4KB | — |
| Firestore 무료 저장 | 1GiB로 알고 있음(**확인 필요**) | 약 25만~50만 건 |
| 쓰기 | 다듬기 1회에 쓰기 +1 → 2~3에서 3~4 | Spark 하루 쓰기 2만에 더 빨리 닿는다 |
| 결론 | 팀 요금제는 유료라 결제가 붙은 뒤 → **Blaze(종량제) 전환이 사실상 전제** | GCP 비용 0 원칙과 함께 결정 |
